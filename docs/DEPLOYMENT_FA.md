# راهنمای نصب و استقرار NYX، قدم به قدم

> **وضعیت این راهنما:** دستورات build و آزمون محلی اجرا شده‌اند، اما دستورات حساب Cloudflare/Gcore، انتشار واقعی، صورتحساب و URL عمومی در این محیط آزمایش نشده‌اند. نام دکمه‌ها و قیمت‌ها ممکن است تغییر کنند. ابتدا روی دادهٔ آزمایشی و دامنهٔ خودتان امتحان کنید.

## ۰. قبل از هر کاری: کلیدهای افشاشده

1. هر کلید GitHub، Cloudflare، Gcore یا توکن دیگری را که قبلاً در چت فرستاده‌اید **فوراً در صفحهٔ ارائه‌دهنده revoke/delete** کنید. نشست‌های فعال و لاگ دسترسی را هم بررسی و در صورت نیاز ابطال کنید.
2. یک رمز پنل کاملاً جدید و تصادفی، طول ۱۶ تا ۲۵۶ کاراکتر، و در صورت نیاز کلیدهایی با کمترین دسترسی و مدت اعتبار بسازید. MFA حساب ارائه‌دهنده را فعال کنید.
3. **رمز یا کلید جدید را در چت، issue، اسکرین‌شات، مخزن، لاگ یا متن دستور shell قرار ندهید.** از secret manager ارائه‌دهنده یا ورودی تعاملی استفاده کنید. GitHub موجود `ysa-py/panel` است؛ ایجاد مخزن دوم لازم نیست.
4. هزینه، سهمیهٔ پلن، قوانین ارائه‌دهنده و قوانین محل استفاده را خودتان بررسی کنید. رایگان‌بودن کد به معنی رایگان‌بودن D1، درخواست‌ها، شبکه، مدل AI یا استفادهٔ تجاری نیست.

## ۱. دریافت و اجرای محلی

Node.js نسخهٔ ۲۲، npm و Git نصب کنید. مخزن را دریافت کنید و نسخهٔ حاوی این تغییرات را پس از بازبینی PR انتخاب کنید؛ اگر هنوز در `main` ادغام نشده، از شاخهٔ PR استفاده کنید.

```sh
git clone https://github.com/ysa-py/panel.git
cd panel
npm ci
cp .dev.vars.example .dev.vars
```

در یک ویرایشگر محلی، مقدار `NYX_BOOTSTRAP_PASSWORD` در `.dev.vars` را با رمز جدید خود جایگزین کنید. این فایل برای توسعه است و نباید commit شود. سپس:

```sh
npm run check
npm run dev
```

`http://localhost:8787/` کنسول و `/panel` مدیریت کاربران است. D1 این حالت **محلی** است و دادهٔ ابر نیست. برای Pages، جداگانه نمونه را در `pages/.dev.vars` قرار دهید و `npm run dev:pages` بزنید؛ خروجی Wrangler آدرس محلی را می‌گوید. بستن سرور: `Ctrl+C`. AI به‌صورت پیش‌فرض متصل نیست تا توسعهٔ محلی به حساب یا هزینهٔ شبکه احتیاج نداشته باشد.

در حساب جدید، روی نخستین درخواست عملیاتی، جدول‌ها در D1 ساخته و رمز با salt و PBKDF2 ذخیره می‌شود؛ UUID و رمز Trojan ادمین تصادفی‌اند. بدون `GZ_DB` یا رمز معتبر، `/healthz` پاسخ 503 می‌دهد و پروکسی و API فعال نمی‌شوند. صفحهٔ ظاهری کنسول ممکن است بدون داده باز شود.

## ۲. انتشار Cloudflare Workers

1. در Cloudflare وارد حساب شوید. در ترمینال امن خود اجرا کنید:

   ```sh
   npx wrangler login
   npx wrangler d1 create nyx-aethercore
   ```

   خروجی حاوی `database_id` را در حساب خودتان ببینید. این شناسه را به‌جای `local-development-only` در `wrangler.toml` بگذارید. نام Worker در همان فایل باید در حساب شما یکتا باشد. `binding = "GZ_DB"` را تغییر ندهید. از پایگاه آزمایشی مجزا استفاده کنید؛ این فرمان روی حساب واقعی منبع جدید می‌سازد.
2. اول `npm run build` را اجرا کنید؛ این **dry-run** است. سپس در صورت موافقت با هزینه و دسترسی حساب:

   ```sh
   npx wrangler deploy
   npx wrangler secret put NYX_BOOTSTRAP_PASSWORD
   ```

   در prompt دوم رمز جدید را روی دستگاه خود وارد کنید؛ آن را به دستور، فایل یا چت اضافه نکنید. اگر لازم شد پس از افزودن secret دوباره `npx wrangler deploy` بزنید. بین انتشار اولیه و تنظیم secret، سرویس عملیاتی باید بسته/503 بماند. `wrangler deploy` نشانی Worker و نتیجهٔ واقعی انتشار را نشان می‌دهد؛ این پروژه نشانی از پیش‌ساخته ندارد.
3. نشانی واقعی Worker را با HTTPS باز کنید، `/healthz` را بررسی کنید و در `/panel` با رمز اولیه وارد شوید. در `/console` گزینهٔ مدیریت به همان پنل وصل است. یک کاربر آزمایشی بسازید، اشتراک را فقط از مسیر امن به کلاینت خود منتقل کنید و **واقعاً** اتصال را روی شبکه‌های موردنیاز آزمایش کنید.
4. پس از راه‌اندازی و ثبت یک پشتیبان، می‌توانید secret اولیه را با `npx wrangler secret delete NYX_BOOTSTRAP_PASSWORD` از Worker حذف کنید؛ رمز hashشده در D1 باقی می‌ماند. اگر بعداً D1 خالی جدیدی ببندید، تا تنظیم secret جدید سرویس بسته می‌ماند. برای تغییر رمز پنل از تنظیمات خود پنل استفاده کنید، نه با فرض اینکه تغییر secret، رمز ثبت‌شده در D1 را عوض می‌کند.
5. در ارائه‌دهنده تا حد امکان **Access/WAF، MFA، نرخ مجاز، بازبینی لاگ و حفاظت ادمین** را فعال کنید. لاگ کامل URL اشتراک، هدر WebSocket و بدنهٔ درخواست‌ها را ذخیره نکنید. یک توکن اشتراک یا پشتیبان، اطلاعات حساس کاربر است.

`wrangler.toml` فعلاً اتصال Workers AI را کامنت کرده است؛ بدون فعال‌سازی صریح بخش ۵ هزینهٔ AI ایجاد نکنید.

## ۳. انتشار Cloudflare Pages Functions

Pages و Workers را دو استقرار جدا بدانید؛ همزمان روی یک D1 تولیدی ننویسید مگر پس از طراحی سازگاری، پشتیبان و هماهنگی. `functions/[[path]].ts` آداپتور مشترک و `pages/functions/[[path]].ts` ریشهٔ استاندارد پروژهٔ Pages است.

1. در Cloudflare یک پروژهٔ Pages و یک D1 برای آن بسازید؛ یا پس از `wrangler login` از `npx wrangler pages project create` و `npx wrangler d1 create` طبق راهنمای Wrangler استفاده کنید.
2. در `pages/wrangler.toml`، شناسهٔ واقعی D1 را جای `local-development-only` بگذارید، نام پروژه را با نام Pages یکی کنید و `GZ_DB` را حفظ کنید. برای Preview یک D1 **جدا** و secret مجزا در تنظیمات همان محیط انتخاب کنید. `pages_build_output_dir` روی `../public` است.
3. از داخل ریشهٔ Pages منتشر کنید؛ Wrangler Pages مسیر سفارشی `--config` را پشتیبانی نمی‌کند:

   ```sh
   cd pages
   npx wrangler pages deploy ../public --project-name nyx-aethercore-edge-pages
   npx wrangler pages secret put NYX_BOOTSTRAP_PASSWORD --project-name nyx-aethercore-edge-pages
   ```

   نام نمونه را با پروژهٔ خود جایگزین کنید. رمز را فقط در prompt امن وارد کنید. شاخه/محیط Preview و Production را در Pages با دقت انتخاب کنید و bindings و secret هر محیط را در داشبورد بررسی کنید. اگر بعد از تنظیم secrets/bindings لازم بود، مجدداً منتشر کنید. خروجی Pages نشانی واقعی را می‌دهد.
4. `/healthz`، ورود، ایجاد کاربر و **WebSocket واقعی روی دامنهٔ Pages خودتان** را جداگانه تست کنید. build و Miniflare محلی، تضمین پشتیبانی مسیر سوکت در استقرار Pages نیست. Pages در این پروژه handler زمان‌بندی‌شده ندارد؛ گزارش زمان‌بندی‌شدهٔ تلگرام فقط برای Worker است.

## ۴. برنامهٔ مستقل Gcore FastEdge `geo-page`

این قسمت **فقط** IP/کشور/شهر بازدیدکننده را بر اساس metadata پلتفرم نمایش می‌دهد؛ پنل، ذخیره‌سازی اشتراک و پروکسی FastEdge پیاده‌سازی نشده‌اند.

1. در ریشهٔ مخزن:

   ```sh
   npm ci
   npm run build:geo
   npm run test:geo
   ```

   فایل محلی `geo-page/wasm/geo-page.wasm` ساخته می‌شود. خروجی Wasm عمداً در Git نیست. آزمون آن از runtime محلی Gcore استفاده می‌کند؛ نتیجهٔ آن استقرار نیست.
2. در [Gcore Customer Portal](https://portal.gcore.com/) به **FastEdge → HTTP Applications → Applications → Create new application → Upload binary** بروید. همان فایل Wasm را انتخاب کنید، نام `geo-page` را وارد کنید و **Save and deploy** را بزنید. این app به environment variable، secret یا Edge Storage نیاز ندارد؛ موارد اضافی را خالی بگذارید.
3. صفحهٔ جزئیات Gcore **URL واقعی همان حساب** را نشان می‌دهد. آن را خودتان باز کنید و `/healthz` و `/api/me` را امتحان کنید. صفحه origin همان درخواست را نشان می‌دهد، بدون path یا query؛ این مقدار لزوماً تأیید URL عمومی حساب نیست. در `/api/me`، `null` به معنی دادهٔ در دسترس‌نبودن است؛ مکان می‌تواند نادقیق باشد. از این metadata برای احراز هویت یا صورتحساب استفاده نکنید و صحت پاک‌سازی هدرهای کاربر توسط پلتفرم را بررسی کنید. خود app داده را ذخیره یا لاگ نمی‌کند؛ سیاست لاگ Gcore جداگانه است.
4. راهنمای رسمی: [ایجاد HTTP app](https://docs.gcore.com/fastedge/getting-started/create-fastedge-apps)، [CLI محلی](https://docs.gcore.com/fastedge/fastedge-cli)، [SDK](https://github.com/G-Core/FastEdge-sdk-js).

### پلاگین FastEdge، اختیاری

پلاگین Gcore برای محیط‌های پشتیبانی‌شدهٔ خودتان است؛ در این محیط Docker/MCP و ابزار آن نصب یا تأیید نشده‌اند. طبق [راهنمای رسمی پلاگین](https://github.com/G-Core/fastedge-plugin)، در Claude Code می‌توان داخل محیط خود اجرا کرد:

```text
/plugin marketplace add G-Core/gcore-marketplace
/plugin install gcore-fastedge@gcore-marketplace
```

برای Codex/Cursor از بخش مربوط در همان راهنما استفاده کنید. MCP معمولاً Docker لازم دارد. ورود تعاملی Portal را به کلید در فایل پروژه ترجیح دهید؛ در صورت نیاز به کلید، آن را فقط طبق مستندات ارائه‌دهنده، با دسترسی محدود و خارج از پوشهٔ پروژه تنظیم کنید. این مراحل ادعای نصب یا استقرار در حساب شما نیست.

## ۵. AI، آزمون مسیر و تلگرام، همگی اختیاری

### فهرست مدل و پاسخ هوش مصنوعی

پیش‌فرض: `NYX_AI_ENABLED=false`، بدون binding AI، پاسخ محلی rule-based. برای فعال‌سازی روی Worker، ابتدا هزینه و حریم خصوصی را بررسی کنید؛ سپس `[ai]` و `binding = "AI"` را در `wrangler.toml` از کامنت خارج کنید. در Pages همین کار در `pages/wrangler.toml` و محیط مربوط لازم است. سپس در محیط صحیح ارائه‌دهنده تنظیم کنید:

| نام | کاربرد |
| --- | --- |
| `NYX_CF_ACCOUNT_ID` | شناسهٔ حساب Cloudflare برای کشف فهرست مدل |
| `NYX_CF_AI_READ_TOKEN` | توکن حداقلیِ **فقط خواندن فهرست مدل**؛ secret |
| `NYX_AI_MODEL_ALLOWLIST` | نام مدل‌های مجاز، جداشده با ویرگول؛ ابتدا فهرست زنده را در کنسول دریافت و نام معتبر حساب خود را انتخاب کنید |
| `NYX_AI_ENABLED` | فقط مقدار `true` فراخوانی دوردست را روشن می‌کند |
| `NYX_AI_DAILY_LIMIT` | تعداد درخواست مجاز هر روز UTC، ۱ تا ۵۰؛ پیش‌فرض ۵ |

برای Worker می‌توان هر مقدار حساس را با `npx wrangler secret put NAME` به‌صورت تعاملی تنظیم کرد؛ در Pages از secret همان پروژه و محیط استفاده کنید. پس از تغییر binding/config دوباره منتشر کنید. متن سؤال صریحاً به Cloudflare ارسال می‌شود؛ **هرگز رمز، توکن، اشتراک یا دادهٔ حساس را در سؤال نگذارید**. درخواست ناموفق هم سهمیهٔ تعداد را مصرف می‌کند. محدودیت تعداد، سقف هزینه یا neurons نیست. اگر سرویس در دسترس نباشد، پاسخ محلی با برچسب fallback نشان داده می‌شود. AI هیچ عملیات مخرب یا تصمیم packet-path اجرا نمی‌کند. اتصال واقعی و هزینهٔ مدل‌ها هنوز تأیید نشده‌اند.

### عیب‌یابی شبکه

`NYX_PROBE_URLS` را فقط با نشانی‌های HTTPS متعلق به خود یا صریحاً مجاز، جداشده با ویرگول، تنظیم کنید؛ حداکثر ۱۰ نشانی، بدون IP literal، اطلاعات ورود، query یا fragment. برای مثال از دامنه و مسیر health خودتان استفاده کنید. پاسخ redirect دنبال نمی‌شود. سنجش از edge است، نه از سیم‌کارت یا ISP ایرانی؛ رتبه‌بندی تضمین سرعت یا دورزدن DPI نیست. محدودیت نام دامنه، تأیید مالکیت DNS یا دفاع کامل در برابر DNS rebinding نیست.

انتخاب نام ISP در صفحهٔ اشتراک **فقط برچسب** است. در خروجی Xray، در صورت نیاز می‌توانید به URL اشتراک `/xray` دو پارامتر `fraglen` و `fragdelay` با بازه‌های صریح و معتبر اضافه کنید؛ طول حداکثر ۵۰۰ و فاصله حداکثر ۳۰ است. بدون هر دو بازهٔ معتبر، fragment اعمال نمی‌شود. این فقط تولید کانفیگ است و پشتیبانی کلاینت یا اثربخشی شبکه آزمایش نشده است.

### اعلان تلگرام

این نسخه فقط اعلان **یک‌طرفه** به یک chat ثابت دارد، نه ربات تعاملی، پرداخت یا فروش. در BotFather ربات خودتان را بسازید و شناسهٔ chat مجاز را خصوصی پیدا کنید. `NYX_TELEGRAM_BOT_TOKEN` و `NYX_TELEGRAM_CHAT_ID` را به‌عنوان secretهای Worker یا Pages قرار دهید؛ هرگز در URL قابل مشاهده، مخزن یا چت کپی نکنید. در کنسول → راهنما، دکمهٔ پیام آزمایشی تنها بعد از ورود و تنظیم هر دو secret فعال می‌شود. تست محلی با API شبیه‌سازی‌شده بوده و تحویل واقعی تأیید نشده است.

برای گزارش مجموع روزانهٔ اختیاری **فقط در Worker**، `NYX_TELEGRAM_DAILY_REPORT=true` را تنظیم و در `wrangler.toml` اضافه و مجدداً deploy کنید:

```toml
[triggers]
crons = ["0 9 * * *"] # هر روز 09:00 UTC
```

فقط تعداد کاربران، تعداد مجاز در لحظه و بایت‌های ثبت‌شده ارسال می‌شوند؛ اینها صورتحساب نیستند. D1 برای هر روز یک تلاش رزرو می‌کند؛ در صورت شکست آن روز خودکار تکرار نمی‌شود. Cron، provider و لاگ ممکن است هزینه داشته باشند.

## ۶. پشتیبان و بازیابی با D1

این پروژه فعلاً پشتیبان‌گیری خودکار یا دکمهٔ restore ندارد. [ابزار رسمی D1](https://developers.cloudflare.com/d1/best-practices/import-export-data/) را به‌صورت دستی و فقط در حساب خود استفاده کنید. خروجی شامل hash رمز، UUID، رمزهای Trojan و اطلاعات کاربران است؛ آن را مانند رمز اصلی محافظت کنید. Export ممکن است درخواست‌های دیگر D1 را موقتاً مسدود کند و بایت‌های اتصال‌های باز هنوز در D1 ثبت نشده باشند.

نمونه روی سیستم Unix با GnuPG، در مکانی خصوصی و **خارج از مخزن**:

```sh
umask 077
mkdir -p "$HOME/nyx-backups"
chmod 700 "$HOME/nyx-backups"
npx wrangler d1 export nyx-aethercore --remote --output="$HOME/nyx-backups/nyx.sql"
gpg --symmetric --cipher-algo AES256 --output "$HOME/nyx-backups/nyx.sql.gpg" "$HOME/nyx-backups/nyx.sql"
```

GPG رمز جداگانه را تعاملی می‌پرسد؛ آن را در مدیر رمز نگهداری کنید. قبل از کنارگذاشتن نسخهٔ plaintext، امکان رمزگشایی و نگهداری امن نسخهٔ رمز‌شده را در محیط خصوصی بررسی کنید. پاک‌سازی روی SSD یا فضای ابری ممکن است بازیابی‌ناپذیری را تضمین نکند. هرگز فایل SQL یا کلید را commit نکنید.

برای آزمایش بازیابی، نوشتن برنامه را متوقف کنید، **یک D1 کاملاً جدید** با نام مجزا بسازید، فایل را فقط در پوشهٔ خصوصی رمزگشایی کنید و `npx wrangler d1 execute NAME-OF-NEW-DB --remote --file=PATH-TO-RESTORED-SQL` را برای همان پایگاه تازه اجرا کنید. ابتدا جداول، تعداد رکوردها، ورود و اتصال را روی محیط تست بررسی کنید؛ سپس در صورت تأیید binding برنامه را به ID پایگاه جدید تغییر دهید. پایگاه اصلی را حذف یا overwrite نکنید؛ راه بازگشت را حفظ کنید. عملیات واقعی export/import اینجا تأیید نشده‌اند.

## ۷. مهاجرت و محدودیت مهم

- از نسخهٔ قبلی Gozargah، طول token اشتراک از ۲۰ به ۳۲ رقم hex تغییر کرده است؛ لینک‌های قدیمی ممکن است 404 شوند. پس از پشتیبان‌گیری، لینک‌های جدید را برای کاربران بازتوزیع کنید. رمز/UUID ذخیره‌شده به‌صورت خودکار تغییر نمی‌کند. نشست‌های قدیمی به‌دلیل تغییر امضای session ممکن است منقضی شوند.
- مسیر WebSocket تولیدشده اکنون `/tunnel` است و early data پیش‌فرض خاموش است تا UUID در path و credential در header قرار نگیرد. handler هنوز path قدیمی و early data صریح را می‌پذیرد؛ early data می‌تواند credential را در هدر آشکار کند. QR پنل از GET به POST تغییر کرده است.
- مجموعهٔ preset منتسب به سایر پروژه‌ها حذف شده و انتخاب ISP صرفاً برچسب است؛ تنظیم fragment اکنون دستی است. این تغییر و تست‌های baselineِ تطبیق‌داده‌شده عمداً مستند شده‌اند.
- هنگام استفاده از D1 قدیمی، رمز پیش‌فرض ضعیف ممکن است همچنان در دادهٔ قبلی وجود داشته باشد؛ بلافاصله از طریق پنل آن را تغییر دهید. هیچ مهاجرت خودکار مخرب یا پاک‌کردن پایگاه انجام نمی‌شود.
- محدودیت چند اتصال/ایزوله، تأخیر cache، قطعی، quota، امنیت ورودی، IPv6، گواهی، کلاینت‌های واقعی و ترافیک ایران باید در محیط واقعی مستقلاً آزموده شوند. Shadowsocks، UDP، پرداخت، محدودیت دستگاه، مدیریت کامل Gcore، ربات تعاملی، HA و صورتحساب تولیدی در این نسخه وجود ندارند.
